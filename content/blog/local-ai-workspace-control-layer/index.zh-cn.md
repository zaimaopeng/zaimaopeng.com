最近我做了一件很有用的 AI 基础设施工作，但它表面上看起来一点都不像 AI 功能。

它是一次工作区边界修复。

这件事听起来很普通，直到你真的开始让一个长期运行的 AI 工作系统同时面对真实项目、共享文件夹、改过名字的目录、项目日志、自动化脚本，以及多个需要共同理解路径的 Agent。

这次真正的问题很简单：给人用的共享项目语料，和给 AI 用的本地工作区控制层，开始漂移了。

有些共享文件夹被重命名了。有些本地入口还指向旧位置。有些项目本来应该放在人能协作的共享空间里，有些项目其实只是 OpenClaw 和 Codex 自己的控制层工作。对人来说，这看起来像普通文件管理。对 Agent 来说，它同时是 routing 问题、记忆问题和可靠性问题。

这就是我觉得值得写下来的地方。

本地 AI 工作区不是“放了一堆文件的文件夹”。一旦 Agent 开始依赖它做记忆、路由、项目状态判断和执行，工作区本身就变成了系统智能的一部分。

而这样的系统需要一个控制层。

## 问题其实很日常

这次问题不是来自什么戏剧性的模型错误。

它来自真实工作里最常见的事情。

一个共享项目文件夹改名了。一个项目从 planned 进入 active。一个旧名字还在过去的引用里出现。一个曾经有用的本地副本变成了 stale copy。一个目录还存在，但它已经不再指向 Agent 以为的那个东西。

对人来说，这很烦，但通常还能手动补救。打开文件夹，看一眼哪里不对，到处搜一下，再手动修掉。

对长期运行的 Agent 来说，这种漂移更危险。

Agent 不只是读文件。它会围绕路径建立假设。它把项目 handle 当成稳定引用，通过已知入口路由任务，把日志写回预期位置，再从这些表面总结项目状态。

所以，一个坏掉的项目入口不只是坏掉的快捷方式。

它会变成错误上下文。

系统可能因为一个目录存在，就以为项目可用。也可能因为真实文件夹移动了，就以为项目变旧了。还可能因为旧引用更容易解析，继续保留一个已经不该作为主入口的名字。问题不是 Agent 不会思考，而是它用来思考的地面已经移动了。

## 真正有用的边界

这次修复变清楚，是从停止把所有东西都当成同一个工作区开始的。

其实有两个表面。

第一个表面，是共享项目语料。这里放的是给人用、给协作使用的项目文件：工作文档、项目材料、共享笔记和协作内容。它需要能被 Agent 系统之外的人访问，也需要能承受普通人的编辑和整理。对共享项目来说，这里应该是 canonical storage。

第二个表面，是 AI 面向的控制层。这里放的是 OpenClaw 和 Codex 需要稳定读取的 handle、项目日志、路由表面、生成出来的状态板、registry 元数据和自动化入口。它需要对 Agent 可预测，不能因为人把某个共享文件夹移动或改名了就悄悄失效。

这两个表面有关联，但不是同一个东西。

这个区分改变了整个结构。

共享项目可以继续放在共享语料里，同时通过稳定入口暴露给本地 AI 工作区。内部项目、源码 checkout 和控制层实验可以继续留在本地。退役的旧名字可以变成很小的 archived alias，而不是坏掉的路径。项目状态可以放进 registry，而不是盲目从物理文件夹所在 shelf 推断。

这听起来像管理杂务，但本质上是可靠性功能。

## 项目需要一个契约

更深一层的教训是，如果希望 Agent 能长期操作一个项目，那项目就不能只是一个文件夹。

它需要一个最低限度的契约。

对人来说，项目需要一个能读的概览和一份当前日志。打开入口以后，应该能知道这个项目是什么，最近发生了什么，真正的文件在哪里。

对 Agent 来说，项目需要一个稳定 handle、一个明确的 path model、一个记录下来的 owner 或 domain、一个 operational status，以及一种验证物理路径是否还指向正确位置的方法。

对自动化来说，创建项目和移动项目最好都脚本化到足够程度，让 registry、workspace entrypoint、shared storage folder、PROJECT_LOG、生成出来的项目板和健康检查一起变化。

否则，每个项目都会变成一个小例外。

一个例外没关系。十个例外就是系统漂移。漂移会变成 stale context。stale context 最后会变成错误自动化。

## 这次实际改了什么

这次修复把边界变成了显式结构。

我们把共享项目语料定义成人类协作项目的 canonical storage surface。

我们把本地 workspace 定义成 OpenClaw 面向的 control and execution layer。

我们重建了项目 registry，并从 registry 重新生成了人能读的项目状态板。

我们加了 physical surface audit，让系统能检查 workspace 入口是否还真的能解析到正确位置。

我们记录了几类路径：共享入口、本地内部项目、退役别名。

我们收紧了新建项目和移动项目的流程，让以后的变更同时更新文件夹、registry、项目日志、生成板和 audit，而不是靠人记忆。

我们也保留了可见债务。有几个源码或 workflow 项目还需要更好的日志。系统没有假装一切完美，而是把它们写成 visible governance debt。

这一点很重要。

控制层的目标不是让系统看起来干净。

而是让系统诚实。

## 为什么这对 Agent 重要

我们讨论 AI Agent 时，常常会把主要限制归结为推理能力。

有时候确实是。

但在一个真实本地工作区里，很多失败来自更普通的机制问题。

Agent 找不到正确文件。项目 handle 指向旧路径。source of truth 在一个地方，自动化读的是另一个地方。生成出来的项目板看起来很新，但背后的 registry 已经漂移。文件夹名字变了，但没有任何地方告诉系统，这个项目的语义身份其实没有变。

这些问题都不炫。

但它们决定 Agent 到底有没有用。

长期运行的 Agent 需要稳定地面。它需要知道哪些名字是长期引用，哪些路径只是物理存储，哪些文件是控制表面，哪些状态标签真的被验证过。

否则，它就会像很多软件系统一样，在模糊状态下非常自信地操作旧假设。

## 更大的教训

这次修复让我更确认：工作区设计本身就是 AI 系统设计的一部分。

记忆不只是 embedding 和 context window。它也是路径稳定性、命名纪律、健康检查、项目日志，以及能够诚实报告状态的控制表面。

自动化不只是模型调用。它也是那些让 source-of-truth 边界不至于慢慢溶解的普通机械结构。

Agent 不只是 prompt。它也是它所居住的环境。

我越是同时使用 OpenClaw 和 Codex，就越在意这类基础设施。不是因为文件夹规则本身多么令人兴奋，而是因为没有这些规则，系统会慢慢失去判断真实工作到底在哪里的能力。

这才是我真正想避免的安静失败。

一个本地 AI 工作区不应该只是一堆文件加上一个 Agent。

它应该是真实工作之上的一个活的控制层：稳定到 Agent 可以信任，明确到人可以检查，也诚实到当地面移动时不会假装没事。
