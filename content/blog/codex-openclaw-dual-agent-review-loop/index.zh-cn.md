最近我围绕 Codex 和 OpenClaw 做了不少事。

有些已经写成了文章。比如我用 Codex 给整个 AI 工作系统做了一次受控的大修补，修 routing、worker 分工、validation loop 和发布链路。也写过 OpenClaw 的状态完整性问题，Watchdog 为什么会静默失效，以及 Anchor 系统为什么从一个脚本问题变成了一个可持续维护的问题。

但还有一个更底层的变化，我之前一直没有单独写。

我开始认真依赖一种双 Agent 评审回路。

这件事听起来像是“让两个 AI 一起干活”。但它真正有意思的地方，不是并行，也不是热闹，而是角色边界。

一个 Agent 负责连续性、上下文和日常运行。另一个 Agent 负责外部视角、局部手术和审查压力。人不退出系统，而是保留最后的判断权，决定什么算完成，什么只是看起来完成。

## 最近真正推进了什么

如果把近期工作压缩成几条线，大概是这样：

第一条线，是 OpenClaw 继续承担长期运行的工作系统角色。它负责记忆、项目、每日协作、工作流入口、文章生产和内部知识整理。它不是一个一次性聊天窗口，而是一个持续存在的本地工作层。

第二条线，是 Codex 开始成为一个更适合做外部检查和局部改造的执行面。它适合进入一个明确边界，读文件、改代码、修脚本、跑验证、总结风险，然后把结果交还给主流程。

第三条线，是我们越来越多地把“完成”从一个语气词变成一个可验证状态。比如 production draft exists 不等于 publish-ready，repo synced 不等于 published，pushed to GitHub 不等于 live page verified。只要这些状态没有被验证，系统就不能假装自己完成了。

这三条线合在一起，才产生了这篇文章真正想写的东西：不是单个 Agent 变强，而是 Agent 之间开始形成一种有用的互相制约结构。

## 还有哪些题目暂时没写

这轮工作其实还能拆出几个暂时没系统写过的选题。

第一个，是双 Agent 评审回路：Codex 和 OpenClaw 如何分工，为什么一个持续运行的 Agent 需要一个外部执行和审查面，以及这种结构怎样减少假完成。

第二个，是“状态诚实性”本身：为什么很多 AI 工作流的问题不是能力不足，而是状态标签太乐观，系统把“我有一个文件”“我跑过一次”“我已经推送”误认为“这件事真的完成了”。

第三个，是本地 AI 工作系统的操作纪律：路径、脚本、发布检查、敏感性扫描、运行日志和 live verification 这些看起来很普通的东西，怎样决定一个系统到底是 demo，还是生产工具。

我最后先选第一个。

因为双 Agent 评审回路是更上层的结构。它解释了为什么后面两件事能被持续发现和修正。

## 双 Agent 不等于两个 Agent 叠加

最容易误解的地方是，以为双 Agent 就是把任务扔给两个模型，让它们各自做一遍，然后取一个更好的结果。

这不是我现在真正需要的东西。

我需要的不是重复劳动，而是不同职责之间的张力。

OpenClaw 更像是长期上下文的持有者。它知道哪些项目正在推进，哪些路径是本地工作系统的默认入口，哪些规则来自过去的事故，哪些状态不能乱报。它的优势是连续性。

Codex 更像是一个可以被明确派进来的外部工作者。它不应该假装自己拥有整个生活史和系统史，但它可以在一个边界里做非常扎实的检查和改造。它的优势是局部执行力和审查压力。

当这两个角色混在一起时，系统会变糊。

长期 Agent 容易因为太熟悉自己的语境而相信已有状态。外部 Agent 容易因为缺少历史而过度自信。人如果把判断权完全交出去，系统就会越来越容易把“看起来对”当成“已经对”。

所以关键不是让两个 Agent 互相替代，而是让它们互相补位。

## 这个回路实际怎么工作

一个健康的双 Agent 回路，大概会长这样：

OpenClaw 提出一个需要处理的问题，或者从长期运行中暴露出一个需要审查的状态。

Codex 进入一个明确边界：检查某个目录、某个发布流程、某个脚本、某个工作流状态，或者某一篇文章是否真的能从 production 同步到站点。

Codex 不只给建议，而是尽量产出可验证的结果：补丁、检查输出、失败原因、待确认项，或者可以被重新运行的命令。

OpenClaw 或人类操作者再把结果放回长期系统里：更新工作流、改状态、关闭任务、留下记录，或者决定这次结果还不能算完成。

这中间最重要的不是谁更聪明，而是谁承担什么责任。

如果 Codex 做的是局部执行，它就应该对文件、测试、构建和差异负责。如果 OpenClaw 做的是长期协调，它就应该对记忆、状态、上下文和后续承接负责。如果人做的是判断，就不能把判断权伪装成“模型已经说可以了”。

## 为什么这能减少假完成

假完成往往不是来自恶意，而是来自系统没有足够的摩擦。

一个 Agent 写了文件，容易说“文章已准备好”。但文章有没有 frontmatter？有没有裸日期？有没有同步到 Hugo？本地 build 是否生成了中英文页面？线上 sitemap 是否真的出现了 slug？这些都需要验证。

一个 Agent 看到 Watchdog 配置存在，容易说“自动恢复已经配置”。但配置存在不等于触发时能跑。状态是 Ready 不等于任务真的会成功执行。

一个 Agent 看到 skill 文件存在，容易说“这个 skill 已经可用”。但如果 routing、references、helper scripts 和 validation 不能一起跑，它就只是一个文件。

双 Agent 回路的价值，是把这些“看起来已经可以了”的地方重新放到审查压力下。

OpenClaw 的长期上下文能提醒 Codex：这里以前出过什么事故，哪些状态不能轻信。Codex 的外部执行面能反过来逼 OpenClaw：别只记录一个结论，把验证跑出来，把输出留下来，把失败说清楚。

这种互相约束比单纯让模型更强更重要。

## 人仍然在回路里

我越来越不喜欢把这类系统描述成“自动化替代人”。

至少在我现在的用法里，更准确的说法是：AI 把很多局部执行和检查的成本降下来了，所以人可以把更多注意力放在判断、取舍和系统形状上。

双 Agent 回路不是为了让人消失。

它是为了让人不必亲自做每一个低层检查，但仍然能看见足够多的证据来做判断。

这也是为什么我会在发布工作流里坚持区分状态。生产稿存在、本地检查通过、推送成功、线上页面可见，这些都是不同状态。它们之间不能靠信心跳过去。

如果系统不能诚实地区分这些状态，它就迟早会把自己说服。

## 更大的教训

最近这些工作让我越来越相信，一个长期有用的 AI 工作系统，不应该只追求一个更强的 Agent。

它应该追求更好的关系结构。

谁持有上下文？谁做局部执行？谁提供外部审查？谁负责验证？谁有权宣布完成？这些问题，比“模型能不能再聪明一点”更接近真实生产系统的核心。

Codex 和 OpenClaw 的组合之所以有价值，不是因为两个名字叠在一起更厉害。

而是因为它们开始形成一个回路：长期上下文提出问题，外部执行面施加审查，验证结果回到系统，人保留最后判断。

这篇文章算是给这个变化留一个标记。

我以前更关注单个能力：能不能写，能不能查，能不能修，能不能发。

现在我更关注回路本身：能不能互相纠偏，能不能留下证据，能不能抵抗假完成，能不能让一个真实工作系统在变复杂以后仍然保持诚实。

这可能才是我最近从 Codex 和 OpenClaw 里真正学到的新东西。
