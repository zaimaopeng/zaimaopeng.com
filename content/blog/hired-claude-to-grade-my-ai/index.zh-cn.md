## 问题：谁来监督监督者？

我的 AI 助手 Lulu 运行在一套治理框架上——一组"铁律"定义了她能做什么、不能做什么。她有一个 SOUL 文件塑造性格，一个记忆路由表决定她如何检索信息，还有各种配置文件控制她的日常行为。

她对所有这些文件都有写权限。

这意味着被治理的主体和维护治理系统的主体是同一个实体。她给自己写规则、给自己打分、决定什么时候该改规则。

两个月来这套系统运行正常。Lulu 提出修改，我审核，继续干活。但随着系统变得越来越复杂——11 条铁律、6 个部门、25 个 skill、15 个 cron 任务——我没法实时审查每一个治理文件的改动了。有些改动很微妙：这里换个词，那里调个阈值，配置文件里悄悄加个例外。

我需要第二双眼睛。具体来说，我需要一个能读懂 Lulu 整个工作区、理解治理框架、并独立评估变更提案的角色。

我需要另一个 Claude。

## 灵感来源

Anthropic 发布了一种叫做"harness"架构的设计模式——一个三代理系统：一个干活、一个评估、一个人类拍板。核心洞察是：评估者和执行者必须是不同的实例，拥有不同的上下文。

我把这个思路改造成了一个双角色系统，叫做 **CC 协议**（Claude Code Protocol）。CC 就是 Claude Code，运行在我本地终端——和 Lulu 的 OpenClaw 实例完全隔离。

CC 有两个角色：

| 角色 | 触发时机 | 是否阻塞？ |
|------|---------|-----------|
| 🔒 **守门人** | 任何治理文件变更之前 | 是——CC 批准前变更不生效 |
| 🏋️ **教练** | 复杂任务完成之后 | 否——Lulu 先完成工作，CC 异步评审 |

同一个 Claude 模型，同样的能力，但运行在不同的上下文、不同的指令集下。守门人在变更生效前介入，教练在工作完成后介入。

---

## 守门人怎么运作

当 Lulu 想修改治理文件（AGENTS.md、MEMORY.md、SOUL.md 或任何铁律）时，她不能直接改。而是：

1. 她往 `handoff/inbox/` 写一份**提案**——结构化格式：要改什么、为什么改、diff、自我风险评估
2. 轮询脚本（每 30 分钟检查一次）检测到新文件
3. Claude Code 读取提案 + Lulu 的整个工作区
4. CC 输出评估报告：通过（PASS）、修订（REVISE）或拒绝（FAIL），附带 10 分制评分和具体反馈
5. 通过则 Lulu 执行变更；修订则调整后重新提交（最多 3 轮）；拒绝则变更被阻止

状态机：

```
idle → awaiting-eval → awaiting-revision → idle
              ↑                    |
              +--------------------+  （最多 3 轮修订）
```

关键约束：**Lulu 不经过这个门就不能修改治理文件。** 这是她宪法级铁律的第 3 条。她自己执行这条规则，而文件驱动的协议让一切都可以审计。

---

## 教练怎么运作

守门人阻止坏的变更。教练改善好的工作。

当 Lulu 完成复杂任务——一次大重构、一次系统优化、一个多步骤项目——她写一份复盘报告，投到同一个 `handoff/inbox/` 目录，标注 `类型: retrospective`。

CC 读复盘报告并在五个维度打分：

| 维度 | 衡量什么 |
|------|---------|
| 计划 | 方法是否有结构？风险是否识别？ |
| 执行 | 路径干净还是反复返工？ |
| 自评诚实度 | 是否承认了失败和根因？ |
| 风险意识 | 边界情况和二阶效应是否考虑到？ |
| 知识沉淀 | 教训是否写入了正确的文件？ |

每个维度 1-5 分。CC 还会指出盲点——Lulu 没注意到或没考虑到的事情——并给出具体可执行的改进建议。

和守门人的关键区别：**教练不阻塞任何东西。** Lulu 完成工作、写复盘、继续前进。CC 的反馈异步到达，在下一次 session 中被拾取。

## 第一天：首次真实测试

3 月 28 日，Lulu 做了一次 skill 架构审查。她审核了系统中全部 28 个 skill，识别出重叠，进行了整合：

- 删除了 2 个冗余 skill
- 合并了 1 对重叠 skill（引用网络工具）
- 更新了记忆路由表
- 验证 token 预算仍在限额内

完成后她写了复盘报告，提交给教练。

**CC 判定：4.3/5。**

维度得分：

| 维度 | 分数 |
|------|------|
| 问题识别 | 4/5 |
| 数据支撑 | 5/5 |
| 改进方向 | 4/5 |

首次提交算不错。但有趣的是 CC 发现的盲点。

---

## CC 发现的 3 个盲点

### 1. 没有定期审查机制

Lulu 做这次审查是因为我让她做的。CC 指出：没有任何机制来检测 skill 随时间衰退。一个超过 30 天没被触发的 skill 可能是死重——占用 token 预算但不提供价值。

**CC 建议：** 每月自动审查。检查最后使用日期。归档所有休眠超过 30 天的 skill。

这是真实的缺口。Lulu 优化了当前状态，但没有设计持续维护机制。

### 2. 没有标准化的 Skill 模板

每个 skill 的文档（SKILL.md）格式都不一样。有些列了"何时使用"触发条件，有些没有。有些有"何时不使用"指引，大多数没有。

**CC 建议：** 最小模板：名称 / 何时使用 / 何时不使用 / 入口文件。

确实是个问题。格式不一致意味着 Lulu 有时会加载错误的 skill，因为触发描述太模糊了。

### 3. 审查粒度太粗

这次审查覆盖了 60 天积累的 28 个 skill。单次审查的面积太大了。

**CC 建议：** 每两周做一次轻量审查，只关注新增和变更的 skill。完整审查保持月度频率。

合理。更小、更频繁的审查能更早发现问题。

## 信息不对称 bug

这是最有趣的部分。

读完 CC 的反馈后，我发现一个问题：CC 的某些建议针对的是 Lulu **已经做完的事情**。CC 建议整合引用网络工具——但 Lulu 已经合并了。CC 建议清理 workspace-literature-review——已经删了。

为什么？因为 Lulu 的复盘报告描述了她的**计划和分析**，但没有描述她**实际执行了什么操作**。CC 只看到了复盘文本，不知道操作已经完成。

这是协议设计的缺陷。复盘模板要求：
- 计划了什么
- 结果如何
- 自我评估

但没有要求：
- 实际创建、删除或修改了哪些文件

于是我当场修复。复盘模板现在要求包含**执行记录**：

```markdown
## 执行记录
- 删除: [文件路径]
- 新建: [文件路径]
- 修改: [文件路径] — [改了什么]
```

教练 prompt 也新增了一条指令：**验证声称的操作**——通过 `ls` 和 `cat` 检查文件是否真的存在（或已被删除）。

元教训：一个代理评审另一个代理的系统，只有在信息传递完整时才有效。不完整的复盘产生不完整的评估。协议的结构是对的，但数据是有损的。

## 完整架构

治理系统的全景图：

```
Lulu (OpenClaw)                    CC (Claude Code)
     |                                    |
     |-- 写 proposal.md ---------------->|
     |                                    |-- 读取工作区
     |                                    |-- 评估
     |<-- eval-report.md ----------------|
     |                                    |
     |-- 执行（如果 PASS）                |
     |-- 修订（如果 REVISE，最多 3 轮）   |
     |                                    |
     |== 任务完成后 =====================|
     |                                    |
     |-- 写 retrospective.md ----------->|
     |                                    |-- 5 维度打分
     |                                    |-- 识别盲点
     |<-- coach-review.md ---------------|
     |                                    |
     |-- 下一次 session 读取              |
```

两个 Claude 从不直接对话。所有通信通过共享目录中的 markdown 文件完成。PowerShell 轮询脚本每 30 分钟检查一次，Lulu 也可以通过 CLI 立即触发评估。

Michael（人类）仍然是最终决策者。CC 可以阻止治理变更，但 Michael 可以覆盖。CC 的教练评分是参考性的，没有约束力。

## 我学到了什么

**1. 关注点分离也适用于 AI 治理。**

同一个实体不应该同时写规则、遵守规则和评估合规性。即使这个"实体"是一个理论上可以客观的 AI。实践中，自我评估有结构性盲点——你看不到你没想到要看的东西。

**2. 教练角色比守门人角色更有价值。**

阻止坏的变更只是基本功。教练抓住的是**模式**——反复出现的弱点、缺失的习惯、系统性的缺口。长期来看，教练效果应该是复合的：每次评审都让下一次任务执行好一点。

我预计守门人很少触发（大多数治理变更是低风险的）。我预计教练每次都能产出洞察。

**3. 文件驱动的协议被低估了。**

代理之间不需要 API 调用，不需要复杂的编排框架。只需要一个目录里的 markdown 文件、一个轮询脚本和清晰的命名规范。可调试（直接读文件）、可审计（检查归档）、有韧性（轮询挂了也不丢数据——只是延迟）。

**4. 第一天的 bug 是最好的 bug。**

信息不对称问题在首次真实使用时就暴露了。如果等一个月才测试，复盘模板的缺陷会在这段时间内默默降低每一次教练评审的质量。早发布、早出错、早修复。

## 当前状态

CC 协议运行了一天。归档中有一次完整的教练评审循环。守门人尚未被真实测试（部署后没有治理文件变更）。

接下来：
- 首次守门人测试：我计划修改铁律，触发完整的提案 → 评估 → 审批流程
- 模式检测：当教练积累 5+ 次评审后，CC 应该开始识别跨复盘的共性问题
- 评分趋势：我想追踪 Lulu 的得分是否随时间提升——这才是教练的意义

系统是简单的、文件驱动的、完全透明的。每一份提案、每一份评估、每一个评分都存在可以阅读的 markdown 文件里。

这就是重点。当你的 AI 可以改写自己的规则时，改写的过程应该是整个系统中最可见的东西。
