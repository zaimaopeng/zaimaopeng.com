我一开始想要的博客工作流很简单：看最近做了什么，从里面找一个值得写的点，整理成文章，然后发布。

听起来这是一条流程。

真正做起来以后，我发现它其实是三条流程。

第一条是发现：从项目日志、closeout、daily memory、handoff 里找出真正有公共写作价值的信号。第二条是写作：把一个信号变成有开头、有主张、有证据、有结构的文章。第三条是发布：把 production bundle 同步到 Hugo 站点，做本地检查，提交推送，再验证线上页面。

做 `blog-automation` 给我的最大教训，就是这三件事必须分开。

## 第一版能跑，但也暴露了边界

第一版自动化是有用的。它能从最近项目里生成博客候选包，而且这些候选不是空想。几篇候选后来真的进入下游 `blog-publishing` 流程，写成了正式文章，并且通过线上验证。

这其实是很强的验证：runner 能跑，队列能读，候选也足够真实。

但同一轮验证也暴露了风险。

一旦系统能生成一个看起来合理的队列，就很容易让它继续往前走。候选看起来像草稿，草稿看起来像文章，push 成功看起来像发布，脚本返回绿色看起来像事实。

但这些不是同一个状态。

自动化需要尊重这些边界。

## 发现不是写作

上游自动化有价值，是因为它能看到人在忙碌中容易漏掉的模式。

一个项目 closeout 里可能藏着比项目计划更好的文章。一个 daily log 里可能保留了真正的失败原因。一个 handoff 里可能正好有一句话，解释了这件事为什么值得写。

这是发现问题。

它关心的是：

- 这里有没有真实的判断变化？
- 这只是状态更新，还是一次失败暴露了更好的规则？
- 这个角度适不适合公开写？
- 这个 slug 或主题是不是已经发布过？

这些问题和写文章不是一回事。

写文章需要节奏、压缩、段落顺序、双语判断和读者路径。发现层只需要生成一个足够强、足够清楚、足够可审查的候选包。

如果这两层混在一起，系统就会在筛选还没做好时，太早生产出“像文章”的东西。

## 发布更是另一回事

发布有更严格的真实状态要求。

一篇文章不是因为有草稿就算发布。不是因为同步进 repo 就算发布。也不是因为 Git 提交成功就算发布。只有本地输出和线上页面都验证通过，才算真的发布。

所以 `blog-automation` 不应该负责发布。

它的工作是让候选队列保持新鲜、诚实、去重，并且只把值得继续写的东西交给下游。`blog-publishing` 才负责文章本身、production bundle、敏感性检查、Hugo 验证、commit、push 和 live verification。

这个拆分看起来慢一点，但它让系统更值得信任。

## 真正的 hardening 来自 drift

第一批成功运行之后，最有价值的问题出现了：已经发表过的文章又回到了候选队列。

生成器其实已经识别出了 overlap，并且在候选文件里写了 warning。但它没有把候选排除掉。于是队列可以一边写着 “High overlap risk”，一边继续把这篇文章列为 active candidate。

这是一个小实现 bug，但背后的流程教训很大。

警告不是状态转移。

如果一个候选的 slug 已经发布过，系统不应该只是描述问题，而应该阻止它进入 active queue。

修掉这个问题以后，队列变得诚实了。它也重新说明了 active queue 应该是什么：里面应该是仍然值得审查的候选，而不是已经知道不合格、只是在旁边贴了警告标签的项目。

## 我真正想要的是哪一层

目标不是全自动发布。

目标是给写作建立一个更好的上游记忆：它持续扫描真实工作，过滤掉已经发表过的想法，包装出强候选，并且只在值得继续投入时交给下游。

这才是我缺的那一层。

没有它，博客想法会散落在项目日志和 daily notes 里。自动化太激进，又会让弱选题和重复选题太快走向发布。真正有用的是中间这层：选择性强、状态明确、可以审查的候选工作流。

所以，博客自动化需要自己的上游流程。

它不是更多发布胶水。

它是在决定什么东西值得被发布。
