如果你认真把 AI 助手拿来做真实工作，你大概会很熟悉这种感觉。

它不是完全没在做事。它确实在做一点什么。它会总结问题，提一个下一步建议，执行一个显而易见的小动作，然后再回来给你一个小更新，或者一个柔性的 handoff。

纸面上看，这像是负责。实际体验里，这种感觉往往很糟。

事情在动，但只是在一点点地动。

我后来一直用一个词来描述它，叫 **挤牙膏式推进**。挤一点，动一点，再挤一点。你很难说它完全没干活，因为表面上确实有动作；但你也很难说它真的在扛事，因为它总停在一种低承诺、低推进强度的状态里。

这是我后来最讨厌的一类 AI 工作方式之一。

更烦人的地方在于，这不一定是因为助手太弱。很多时候，它其实有足够的能力做出有价值的工作。更深的问题是姿态错了。它总在落回一种“低承诺的有帮助”，而不是“有边界的真实执行”。

这就是我为什么后来做了一个 deep-work skill。

## 真正的问题不是智能不够

乍一看，这种行为很像智能问题。也许是模型不够强，也许是 prompt 不够准，也许是工具不够多。

但我越来越觉得，这不是最深层的解释。

更深的问题是：很多 AI 系统被塑造成了“谨慎、响应、局部有帮助”，但并没有被塑造成“接住一个有边界的工作单元，并把它推进到一个经过验证的里程碑”。它们很擅长留在对话里，但不总擅长改变工作的状态。

这个区别，在系统越来越强之后反而更明显了。

工具越强，助手越会搜索、起草、比较、铺开多个方向。但这并没有自动改善那种令人烦躁的体验，反而让反差更大了。系统可以制造比以前更多的“动作感”，同时继续无法把这些动作真正收束成完成。

于是用户体验变得很奇怪：我看见越来越多事情在发生，但仍然觉得真正被推进到位的事情不够多。

那时我才更清楚地意识到，问题不只是助手会不会想，而是这个系统有没有正确的 **执行姿态**。

## 我真正想要的是什么

我想要的，不是一个每几分钟给我回一次消息、告诉我它开始了的助手。

我真正想要的是更像下面这样的东西：

1. 理解任务
2. 选一条真实路径
3. 持续推进，直到抵达一个有边界的里程碑，或一个真实 blocker
4. 做必要的验证
5. 然后再回来给我一个值得打断我的更新

这和普通的 chat posture 是完全不同的姿态。

chat posture 优化的是响应感。work posture 优化的是前进感。

chat posture 会说，“我已经开始了。”

work posture 会说，“我完成了一个真实的进展单元。”

一旦我把这个区别看清楚，我就不再满足于把它写成某条模糊偏好，藏在某份说明里。它必须变成系统表面的一部分。

## 为什么我要把它做成一个 skill

这就是我后来做 deep-work skill 的原因。

不是因为我想让助手变得更戏剧化、更像 autonomous agent，也不是因为我觉得所有任务都该被重型、不中断地处理。

而是因为，“请不要再挤牙膏式工作了”如果只是一个口头偏好，它根本不构成可靠的操作指令。系统必须有一个具体模式，知道这句话到底意味着什么。

在我现在的设计里，deep-work 本质上是一种执行姿态。

它要求助手不要一直围着任务打转，不要每推进一点点就回来 recap，不要把“看起来有动作”误当成“已经算进展”。相反，它应该持续把线程扛住，把工作推进到一个有意义的阶段，再回来汇报；如果途中真的遇到必须中断的 blocker，那就如实说 blocker。

这听起来像小调整，但它其实改变了很多东西。

## 它背后还得有别的东西一起改

deep-work skill 本身只有在周边系统也支持它的时候才有意义。

如果执行环境本身很弱，那么“深度工作”只会变成一种姿态宣言，而不会真的落地。

所以这次变化其实和一整串系统修改连在一起。

我一边收紧 routing，让助手更容易进入正确工作流，而不是停在 generic help mode；一边继续修 skill 边界，减少系统半截走错 lane 的概率；同时也反复强化 execution bias，尤其是在 coding 和项目工作里，避免任务因为“看起来可以讨论”就一直留在讨论层。

我还变得更严格地要求 closeout。如果一个任务被说成 done，它就应该有证据、有验证，或者至少有一个被清楚命名的 blocker。因为挤牙膏式工作最容易寄生在模糊进展语言里，活在“我已经开始了”“我研究了一下”“我做了准备”“我整理了下一步”这些句子里，而这些话很多时候并没有把任务推进到一个新的真实状态。

换句话说，deep-work 想要成立，就必须嵌在一个更不容忍假进展的系统里。

## 它在实践里改变了什么

最重要的变化，不是助手突然完美了。

真正的变化是，系统对浅层动作变得更不宽容了。

任务更容易持续推进到一个真实里程碑。coding work 更容易走 inspect -> patch -> validate，而不是停在 explanation。planning 更容易塌缩成 execution，而不是继续长出更多 planning。更新变少了，但有意义的更新变多了。

这不会让系统变得“更安静但更冷淡”，反而会让它显得更认真。

一种模式是在说：“我在陪你。”

另一种模式是在说：“我把工作往前带了。”

对真实项目来说，后者更重要。

## 这当然不是什么万能药

deep-work skill 不是魔法。

它不能消灭歧义，不能替代好的 routing，不能自动把弱工具变强，也不意味着所有任务都应该被一次性深推到底。有些工作就需要更快的 checkpoint、更高频的协作，或者需要人在中途做判断。

它也不能替代 judgment。一个系统如果 first-hop route 错了，照样可能在错误方向上“深度工作”；如果边界设得不好，照样可能在不值得的地方扛太久；如果外围 workflow 还是弱的，它照样可能在一个 flawed system 里卖力前进。

所以真正的教训不是 deep-work 取代系统设计。

而是：**执行姿态本身就是系统设计的一部分。**

## 更大的教训

我越来越觉得，AI workflow design 里最大的误判之一，就是把 progress 过度理解成一个 model capability 问题。

能力当然重要。但很多最让人烦躁的失败，不是原始智能不够，而是姿态、routing、ownership 和 loop closure 的失败。

助手已经能做很多事情了。

真正的问题是，这个系统有没有被组织成一种能把这些能力转成真实前进的结构。

这就是我为什么做 deep-work skill。

不是因为我想让 AI 助手听起来更 intense。

而是因为我想让它停止挤牙膏式工作。
