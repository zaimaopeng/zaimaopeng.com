# 知识越积越多，为什么检索反而会越来越差

最近我一直在升级 OpenClaw 的记忆检索系统。真正让我越来越在意这件事的，不是“记忆”这个概念本身，而是一个更实际的问题：知识系统最危险的时候，往往不是它太小，而是它开始变大之后。

系统小时候，很多问题都不是真问题。文档不多，目录不深，大致知道东西放在哪里，检索不够聪明也还能靠人脑补回来。但一旦你开始持续地往里面写 daily log、项目文档、部门知识、技术笔记、写作草稿，事情就变了。知识当然在增长，但搜索负担也在增长，性能压力也在增长，而检索质量不一定同步提高。很多系统不是死在没有知识，而是死在知识积累到后面，开始反过来拖累自己。

这也是我最近一直在想的一件事：怎么才能让知识继续扩张，但不要把未来的检索成本也一起推高。也是在这个过程中，我越来越确认 Anchor 是绕不过去的一层。

原因其实很简单。文档被写下来时有它当时的措辞，但人以后再去找这份知识的时候，问问题的方式通常已经变了。我们不会总是用写文档时的原句去搜旧知识，我们用的是当下遇到问题时脑子里冒出来的那句话。你写一篇文章，标题可能是“AI 时代深度工作为什么仍然重要”，但以后再找它时，心里想的未必还是这个句子，你更可能会问，AI 时代深度工作到底还有没有意义，为什么最后那 10% 的收敛反而更关键。另一篇文章如果写的是中国古代书衣和函套，未来检索时想到的可能是，中国古代到底有没有“书衣”这种东西，或者书衣和函套的差别是什么。真正决定一篇文档能不能被找回来的，很多时候不是它有没有被写下来，而是未来的提问方式能不能和它对上。

这就是我开始做 Anchor 的原因。我不是先从“优化 embedding”这种技术角度出发的，而是先从一个很朴素的使用体验出发：知识明明已经在系统里了，但系统不一定能按我未来真正会问的方式把它找回来。这个偏差如果不处理，知识越积越多，检索反而越容易变钝。所以我后来越来越觉得，单纯依赖文档原文不够，我们需要提前给文档补一层“如果未来再找它，最自然会怎么问”的入口。Anchor 做的就是这件事。它不是正文，不是摘要，也不是简单列关键词，而是提前替未来的检索过程生成一组更接近真实提问方式的入口。某种意义上，这有点像 reverse HyDE：不是在查询时生成假想文档，而是在索引时生成假想查询。

问题在于，Anchor 一旦被证明有用，它自己马上也会变成一个维护问题。只要系统还在增长，新文档会不断出现，旧文档会不断修改，知识结构会不断重组，Anchor 就不可能是一次性工程。它如果真的重要，就必须被持续维护，而且最好是自动维护。真正要解决的问题，从来都不是“Anchor 有没有用”，而是“Anchor 能不能被稳定地持续维护”。

我们上一轮其实已经做出了一个能工作的原型。当时的思路很直接：扫描目标目录，把文档前一部分送给本地 Ollama 模型，让模型生成几条假想检索问题，再把结果写回 markdown，最后再做 memory index。单看流程，它已经像一条自动化流水线了。但真正跑起来之后，我很快发现它还不算一个真正可用的系统。最先暴露出来的是很无聊、但也很真实的工程问题。比如 Windows 终端编码会把日志层打崩，脚本只是打印一个 Unicode 进度符号，就能直接报 `charmap codec can't encode character '\u2192'`。另外，本地 Ollama 推理的延迟也不稳定，有些文件很快回来，有些文件会卡住很久。

不过这些都还不是最根的问题。最核心的问题是，上一轮的脚本本质上还是一个长进程承担整批任务。它从头跑到尾，所有文件都挂在同一个 Python 进程上。这样一来，只要某个文件超时，或者宿主把长任务 SIGKILL，整批都会一起受影响。如果状态没有及时落盘，前面明明已经做成功的部分，也会在感受上变成“白跑了”。所以我后来对上一轮的判断很明确：它不是没有功能，而是没有真正解决 Anchor 如何被稳定维护的问题。

到了这一轮，我反而没有先去纠结 prompt 要不要再打磨，也没有先去追求模型是不是还能更强一点。因为问题已经很清楚了：不是模型不会生成 Anchor，而是系统无法在真实环境里可靠地把一整批 Anchor 维护任务跑完。也就是说，这次真正要修的不是“内容生成能力”，而是“执行模型”。我后来把这个目标压缩成一句话：单个文件失败，不能拖垮整批任务。

所以这一次我把它重构成了三段式。先用 Planner 去决定谁该被处理，它负责扫描目录、判断哪些文件值得进这一轮队列；再用 Worker 一次只处理一个文件，读文件、调模型、生成假想查询、写回 Anchor，然后退出；最后由 Runner 逐个调度 Worker，并且在每处理完一个文件之后，立刻把状态和结果落到 `auto_anchor_state.json` 和 `auto_anchors.json` 里。这样系统天然就有了 resume、retry、per-file isolation、state persistence 和 interrupted run recovery 这些能力。换句话说，它不再是“一个进程从头跑到尾的长脚本”，而是一条真正能恢复、能续跑的流水线。

这次我不是只改完代码就觉得“应该好了”，而是拿 `departments/` 真正做了验证。最关键的一个现象是，`index.zh-cn.md` 第一次尝试超时了，但第二次重试成功，而且整批任务没有崩。这件事真正说明的不是某个文件最后成功了，而是新的执行模型已经达到了最核心的目标：现实世界可以不完美，模型也可以偶发波动，但系统本身不能因为这种不完美就整体失效。后面的结果也对得上：多个 `departments/content/production/` 下面的文档成功写入了 Anchor，`auto_anchor_state.json` 和 `auto_anchors.json` 成功落盘，之后我再对 `departments` 做 planner + runner 的全量检查，结果 `queued 0 files`，说明按照当前规则，这一轮该补的部分已经处理完了。

所以如果现在再回过头来看“这个问题到底算不算解决”，我的答案是算，而且我觉得可以很明确地说，这已经是一轮完成度足够高的 v1 production upgrade。因为这次真正要解决的问题，从来就不是模型能不能临时写出几条还不错的 query，也不是脚本能不能在理想条件下偶尔跑通，而是 Anchor 能不能被持续维护，自动更新能不能在不稳定环境里可靠执行，单个文件的问题会不会拖垮整批，中断以后能不能继续，而且不丢掉已经完成的结果。现在这些问题都已经被解决了。换句话说，Anchor 的自动维护和自动升级，这一轮已经真正跑通了。

当然，这不等于说它以后没有继续优化的空间。后面当然还可以继续补很多东西，比如更完整的 metrics、自动触发 memory index、只针对新增或修改文件做增量运行、定时调度与告警，不同类型文档走不同生成策略。这些都值得做，但都属于下一层优化，不属于“核心问题还没有解决”。判断一次升级是否成功，看的不是它是不是最终形态，而是它有没有把最关键的断点修掉。这一次修掉的断点，就是 Anchor 维护能力从脆弱脚本变成了可持续运行的系统能力。

我自己做完这一轮之后，一个很强烈的感受是，很多 AI 系统看起来像是模型问题，最后真正决定它能不能长期工作的，反而是一些非常朴素的工程问题：能不能 checkpoint，能不能 retry，有没有状态落盘，能不能隔离失败，能不能恢复执行。真正让一个 AI 功能从 demo 变成基础设施的，往往不是 prompt 本身，而是它有没有被放进一个可靠的执行框架里。Anchor 这次升级，对我来说最重要的地方也在这里。表面上看，好像只是给文档补了一层检索入口；但更本质地说，我们在解决的是另一个更大的问题：当知识持续增长时，系统能不能不被自己的规模反噬。Anchor 当然不是全部答案，但它是这里面一个必要的手段。而这一次，我们终于不只是证明了 Anchor 有用，也把“如何自动维护 Anchor”这件事，真正做成了一条能稳定运行的生产流水线。这才是这次更新真正值得写下来的地方。
